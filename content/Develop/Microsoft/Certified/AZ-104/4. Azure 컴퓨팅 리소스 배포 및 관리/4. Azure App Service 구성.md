# Azure App Service 구현

모든 플랫폼, 디바이스용 웹 사이트, 모바일 백엔드, 웹 API 등 모두 쓸 수 있음. 
Windows, Linux 기반 환경에서 쉽게 실행, 확장 가능함. 
App Service로 여러 제품 빠르게 시작 가능. 

![App Service 빠른 시작을 사용하여 웹, 모바일 및 API 앱을 개발하고 배포할 수 있는 제품을 보여 주는 일러스트레이션](https://learn.microsoft.com/ko-kr/training/wwl-azure/configure-azure-app-services/media/web-quickstarts-c154c8e4.png)

## App Service의 이점

- 여러 언어 & 프레임워크
- DevOps 최적화
- 고가용성 갖춘 글로벌 규모
- SaaS 플랫폼, 온프레미스 데이터 연결
- 보안, 규정 준수
- 애플리케이션 템플릿 선택 가능 (Azure Marketplace)
- Visual Studio 통합
- API, 모바일 기능
- 서버리스 코드

# App Service로 앱 만들기

Azure App Service의 Web Apps, Mobile Apps, API Apps 사용 가능. 
Azure Portal에서 앱 생성 가능. 

## 구성 설정에 대해 알아야 할 사항

- 이름
	- 고유해야 함
	- 사용자 지정 도메인 쓰려면 이 이름과 매핑 가능
- 게시 (호스트)
	- 코드 || Docker 컨테이너로 호스트 가능
- 런타임 스택
	- Azure App Service << 소프트웨어 스택으로 언어, SDK 버전 포함해 앱 실행함
	- Linux 앱 || 컨테이너 앱 << 선택적 시작 명령, 파일 설정 가능
	- 스택 << PHP, .NET Core, Node.js, Python 등 사용 가능
- OS
	- Linux, Windows 사용 가능
- 지역
	- 물리적인 그 지역 위치 << App Service 요금제에 영향 줌
- 가격 책정 계획
	- 사용 가능한 리소스, 기능, 용량 설정 << 앱을 Azure App Service 요금제와 연결해야 함
	- 선택한 (물리적) 지역에서 사용 가능한 가격 계층 중 선택

### 만든 후 설정

앱 생성 후 -> Azure Potral에서 배포 옵션, 경로 매핑 등의 설정 가능

![Azure Portal의 App Service를 사용하는 앱의 다른 구성 옵션을 보여주는 스크린샷.](https://learn.microsoft.com/ko-kr/training/wwl-azure/configure-azure-app-services/media/web-app-configuration-27facdc5.png)

아래는 예시임. 

- Always On
	- 트래픽 없어도 앱 로드된 상태로 유지. 
	- (WebJobs || CRON 언어 식으로 트리거되는 WebJobs)에 필요

	- 다중 인스턴스 배포에서 클라이언트가 세션 수명 동안 같은 인스턴스로 라우팅 되는지 확인 가능

	- 설정 시 모든 HTTP 트래픽이 HTTPS로 리디렉션 됨

# 배포 슬롯 만들기

Azure App Service에 배포 시, 
기본 프로덕션 슬롯 대신 별도의 배포 슬롯 사용 가능. 

## 배포 슬롯에 대해 알아야 할 사항

- 배포 슬롯 << 자체 호스트 이름 갖춘 라이브 앱
- (표준, 프리미엄, 격리) 가격 계층에서 사용 가능
	- 위 계층들은 서로 다른 수의 배포 슬롯 제공함. 
- 앱 콘텐츠, 구성요소 << 프로덕션 포함한 두 배포 슬롯 간 교환 가능

![Azure Portal에서 배포 슬롯을 사용하는 방법을 보여주는 스크린샷.](https://learn.microsoft.com/ko-kr/training/wwl-azure/configure-azure-app-services/media/deployment-slots-5b3660cc.png)

## 고려 사항

- 유효성 검사 고려
	- 프로덕션 슬롯으로 변경내용 푸시 전에, 스테이징 배포 슬롯에서 변경내용 유효성 검사 가능
- 가동 중지 시간 줄이기 고려
	- 슬롯으로 앱 배포 후에 프로덕션으로 교환함
	- 따라서 프로덕션에 올라오기 전에는 준비된 상태임
	- 준비된 상태 옵션 선택 << 앱 배포 시 가동 중지 X
	- 트래픽 리디렉션 중단 X, 프로덕션으로 교환 중 누락되는 요청 X
	- 전환 전 유효성 검사 할 필요 없다면 "자동 전환" 구성하여 전체 워크플로우 자동화 가능
- 마지막으로 알려진 좋은 사이트로 복원 고려
	- 스테이징에서 프로덕션으로 앱이 올라간다고 했죠? 
	- 그럼 원래 프로덕션 자리에 있던 앱이 스테이징으로 내려감
	- 변경된 내용이 예상과 다를 경우에는 교환 작업 즉시 실행함
	- => 이전에 프로덕션에 있던 앱으로 다시 돌아감. 
	- 이전에 프로덕션에 있던 앱 = 마지막으로 알려진 좋은 사이트
		- 대충 이전의 stable한 버전으로 돌아간다는 뜻으로 해석됨. 
- 자동 전환 고려
	- 자동 전환 << 가동 중지 없이 지속적 앱 배포 위한 Azure Pipeline 시나리오 간소화
	- 프로덕션 슬롯으로 자동 교환되면 변경내용 푸시할 때 마다 자동으로 교환해 줌. 
	- 현재 Linux 웹 앱에서는 지원되지 않음

# App Service 앱 보호

App Service << 기본 제공 인증, 권한 부여 지원함.
웹 앱, API, 백엔드, Azure Functions 앱에서 코드 최소 사용으로 로그인, 데이터 접근 가능.

안전한 인증, 권한 부여 위해서는 보안을 잘 알아야겠지. 
App Service가 도와주기 때문에 사용하는 우리는 다른 더 중요한 일에 신경쓰면 됨. 

> 인증, 승인 때문에 Azure App Service 쓸 필요는 없음

## App Service 사용 시 앱 보안에 대해 알아야 할 사항

- 인증, 권한 부여 보안 모듈 << 코드와 동일한 환경에서 *별도로* 실행됨
- 보안 모듈 << 앱 설정으로 구성됨. 코드 변경 *불필요*
- 보안 모듈 사용 << HTTP 요청이 앱에 들어가기 전에 모듈부터 통과함
- 보안 모듈이 처리하는 것들
	- 지정된 공급자(구글로그인 등)로 사용자 인증
	- 토큰 유효성 검사, 저장, 새로고침
	- 인증된 세션 관리
	- 요청 헤더에 ID 정보 삽입

## 앱 보안에 App Service 사용 시 고려사항

- 익명 요청 허용
	- 인증되지 않은 권한 부여 연기
	- 인증됐으면 HTTP 헤더의 인증 정보 또한 전달
	- 익명 요청의 유연한 처리 가능
	- 여러 로그인 공급자 제공 가능
- 인증된 요청만 허용
	- 모든 익명 요청을 `/.auth/login/<provider>`로 리디렉션
	- `<provider>`로 로그인 하는 것과 같음
	- 이 기능 사용 -> 앱에서 인증코드 작성 필요 X
	- 익명 요청이 네이티브 모바일 앱에서 오는 경우
		- `HTTP 401 Unauthorized` 반환

	> 인증된 요청만 허용 << 모든 호출에 대한 접근을 제한함. 
	> 이는 공용 홈페이지 쓰는 경우 바람직하지 않을 수 있음.

- 로깅 및 추적
	- 로그 파일에서 직접 인증, 권한부여 추적
	- 예기치 못한 오류에 대해 모든 세부 정보 쉽게 찾을 수 있음
	- 추적 로그에서 `EasyAuthModule_32/64` 모듈에 대한 참조 찾을 것

# 사용자 지정 도메인 이름 만들기

생성한 웹 앱은 `azurewebsites.net`의 하위 도메인에 할당됨. 
웹 앱 이름이 `consoto`일 때, URL은 `consoto.azurewebsites.net`이 됨. 
또한 가상 IP Addr이 할당됨. 
프로덕션 웹 앱(실제로 사용자에게 배포되는 웹)의 경우는 사용자 지정 도메인 이름 표시 가능함. 

## 앱의 사용자 지정 도메인 이름을 구성하는 단계

사용자 지정 DNS 이름을 웹에 매핑하려면 App Service 요금제 유료 계층이 필요함. 
아무튼 이거 구성하려면 세 단계가 있음.

![Azure Portal의 사용자 지정 도메인 페이지를 보여 주는 스크린샷.](https://learn.microsoft.com/ko-kr/training/wwl-azure/configure-azure-app-services/media/custom-domain.png)

1. 도메인 이름 예약
	- 가장 쉬운 방법: Azure Portal에서 직접 구입 (`\*.azurewebsites.net`이 아님)
	- 타사 사이트로 가는 대신 Azure Portal에서 웹앱 도메인 이름 관리 가능
2. DNS 레코드 생성
	- 도메인을 Azure 웹 앱의 IP Addr에 매핑
	- DNS 레코드의 유형
		- 웹 앱의 경우 `A`레코드 || `CNAME`(Canonical name) 레코드 생성
			- `A`레코드 - 도메인 이름 IP Addr 매핑
			- `CNAME` 레코드 - 도메인과 다른 도메인 매핑
				- DNS는 두번째 이름을 사용해 주소 조회
				- 사용자는 브라우저에서 첫 번째 도메인 봄
				- `contoso.com`을 `webapp.azurewebsites.net` URL로 매핑
		- IP Addr 변경되면 `CNAME`은 유효하지만 `A`레코드 업데이트 해야함
		- 일부 도메인 등록 기관은 루트 도메인 || 와일드카드 도메인에 대한 `CNAME` 레코드 허용하지 않음 -> `A`레코드로 사용할 것
3. 사용자 지정 도메인 사용
	- 도메인 있고, DNS 레코드 만들고, Azure Portal로 유효성 검사 후 추가 가능
	- 게시 전 도메인 테스트 필요

# App Service 앱 백업 및 복원

(수동 || 일정)에 따라 백업 생성 쉽게 가능함. 
(특정 기간 || 무기한) 보존되도록 백업 구성 가능. 
(기존 덮어쓰기 || 다른 앱 or 사이트로 복원 || 이전 스냅샷으로 복원) 가능

## 백업 및 복원에 대해 알아야 할 사항

- (표준 || 프리미엄) 계층의 App Service 요금제 필요
- 백업할 앱과 동일한 구독에 Azure Storage 계정, 컨테이너 필요
- Azure Storage 계정, 컨테이너에 백업 가능한 것들
	- 앱 구성 설정
	- 파일 콘텐츠
	- 앱에 연결된 모든 DB (SQL DB 등)
- 스토리지 계정에서 백업은 Zip, XML 파일로 구성됨
	- Zip - 앱, 사이트에 대한 백업 데이터 포함
	- XML - Zip 파일 콘텐츠의 매니페스트
- 수동 || 일정에 따른 백업
- 기본값 - 전체 백업
- 부분 백업 지원됨 - 설정에서 백업 제외할 파일, 폴더 지정 가능
- 부분 백업 복원 방법 = 정기 백업 복원 방법
- 최대 10GB 앱, DB콘텐츠 저장 가능
- Azure Portal에서 스토리지 계정, 컨테이너 페이지에 백업 표시됨

## 백업 만들고 복원 시 고려해야 할 사항

- 전체 백업 고려
	- 모든 설정과 콘텐츠 저장
	- 복원 시 백업의 항목들로 모두 대체됨
	- 사이트에 있고 백업에 없는 파일은 삭제됨
- 부분 백업 고려
	- 백업 파일 선택 위해 부분 백업 지정
	- 제외된 폴더, 파일의 모든 콘텐츠가 그대로 남아있음
- 백업 파일 검색 고려
	- Zip, XML 파일 찾아 백업에 액세스
	- 복원 수행하지 않고도 콘텐츠 조회 가능
- 백업 대상의 방화벽 고려
	- 스토리지 계정이 방화벽에서 사용하도록 설정 된 경우 - 스토리지 계정은 백업 대상이 될 수 *없음*

# Azure Application Insights 사용

Azure Application Insights << Azure Monitor의 "라이브 애플리케이션 모니터링 가능한" 기능.
앱에서 성능 이상 자동 검색하도록 Application insights, App Service 통합 가능.

Application Insights << 앱 성능, 유용성 지속적 개선 가능.
문제 진단, 수행할 작업 이해에 도움되는 분석 도구 제공. 

## Application Insights에 대해 알아야 할 사항

- .NET, Nodejs, Java EE 등의 플랫폼에서 작동
- 온프레미스, 하이브리드, 퍼블릭 클라우드에서 호스팅 되는 구성에 사용 가능
- Azure pipeline 프로세스와 통합됨 + 다양한 개발 도구와 연결 가능
- Visual Studio App Center 통합 -> 모바일 앱에서 데이터 모니터링, 분석

## Application Insights 사용 시 고려 사항


- 요청 속도, 응답 시간, 실패율 고려
	- 어떤 시간에 어떤 위치에 어떤 페이지가 인기있는지 확인
	- 어떤 페이지가 성능 좋은지 확인
	- 요청 많은데 실패율 높아지면 문제있는거임
- 종속성 비율, 응답 시간, 실패율 고려
	- 외부 서비스가 앱 성능 저하시키는지 조사
- 예외 고려
	- 통계 분석, 인스턴스 스택 추적, 관련 요청 분석
	- 서버, 브라우저 오류 전부 보고됨
- 페이지 보기, 로드 성능 고려
	- 사용자 브라우저에서 보고한 페이지 보기 숫자 수집, 로드 성능 분석
- 사용자, 세션 수 고려
	- 앱에 연결된 사용자, 세션 수 추적에 도움 될 수 있음
- 성능 카운터 고려
	- Windows || Linux 서버 PC에서 Application insights 성능 카운터 추가
	- CPU, MEM, Net 사용량 등의 성능 출력 모니터링
- 호스트 진단 고려
	- Docker, Azure의 진단을 Application Insights에 통합
- 진단 추적 로그 고려
	- 앱에서 추적 로그 구현
	- 추적 이벤트, 요청과 연결
- 사용자 지정 이벤트, 메트릭 고려
	- 사용자 지정 이벤트, 메트릭 주적 알고리즘을 클라이언트 or 서버 코드로 작성
	- 판매된 항목 수 등의 이벤트 추적
